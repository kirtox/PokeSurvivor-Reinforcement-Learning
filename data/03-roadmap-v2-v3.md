# v2 / v3 路線圖

## v1（目前）— 已完成實作，待跑訓練驗證
範圍：固定百變怪、升級卡/道具/連結自動選、關閉天氣/Boss/連線/轉蛋。
目標：閃避＋切招式的核心操作要能明顯超越 baseline（隨機 32.7s / 原地不動 27.9s），
不要求破關或衝高名次。

---

## v2 — 讓 agent 自己選升級卡，挑戰更長存活時間
**動機**：這類「彈幕倖存」遊戲的敵人強度會隨時間持續上升，光靠閃避技巧有天花板——
角色本身要透過升級卡片變強（血量/攻擊/速度/減傷…）才跟得上後期強度。v1 把選卡交給
固定 heuristic（優先 HP/DEF），所以撐不久是預期內的限制。

**要做的事**：
1. 把升級卡選擇也變成 agent 的動作之一：
   - 在 `window.RL.step()` 擴充一個可選參數 `cardIdx`（0-2，對應 3 選一），只有在
     `state === 'levelup'` 時才有意義。
   - 動作空間從 `MultiDiscrete([9,5])` 擴充成 `MultiDiscrete([9,5,3])` 或拆成兩段式
     決策（平時用 9×5，遇到升級畫面時用額外的 3 選一子決策）——需要再討論哪種設計
     對 PPO 比較友善（稀疏、低頻率的決策容易被 9×5 的高頻決策蓋過訊號）。
2. Reward 需要重新檢視：升級選卡的效果是「延遲見效」的（例如加防禦要過一陣子才
   看得出撐久了），單純的即時 shaped reward 可能學不到這個因果關係，可能要加入
   「存活到某個時間檢查點」的額外獎勵，或拉長 PPO 的 `gamma`（更看重長期回報）。
3. 目標：平均存活時間挑戰 **15-20 分鐘**（30 分鐘列在 v3，等核心機制都驗證過再衝）。
4. 重新量測 baseline（固定 heuristic 選卡 vs. agent 自選卡）作為 v2 的比較基準。

## v3 — 全開範圍，挑戰 30 分鐘存活 + 泛化能力
**動機**：v1/v2 都鎖定百變怪；要驗證方法是否通用，且要把使用者原本要的完整遊戲機制
都涵蓋進來。

**要做的事**：
1. **開放角色選擇**：訓練時隨機抽不同起始寶可夢（或至少涵蓋水/火/草/一般系各一隻
   代表），觀察同一個 policy 能否泛化到不同招式機制；或改用「角色也是觀察值的一部分」
   讓 agent 學會依角色調整打法。
2. **重新開啟天氣系統**：天氣會加成/削弱特定屬性，需要把天氣狀態加進觀察向量。
3. **裂隙 Boss 戰**：是獨立的競技場戰鬥，可能需要另外設計一個子任務/子環境，
   或是把「要不要進裂隙」也變成 agent 的決策之一。
4. **連線合作模式**：這是多智能體問題（要考慮隊友位置、復活隊友），複雜度跳一個量級，
   建議當成獨立子專案，不一定要跟主線 agent 共用同一個 policy。
5. **轉蛋/收集要素**：這些是 meta-progression（帳號永久養成），和單局內的 RL 決策
   關聯較低，可能不需要讓 agent 直接控制，而是作為訓練時的固定設定（例如固定用某個
   已經強化過的帳號存檔）。
6. 目標：平均存活時間挑戰 **30 分鐘**，並檢查 policy 能否在未訓練過的角色上也有
   合理表現（泛化能力的量化指標，例如跟同角色訓練的 policy 相比掉了多少 % 存活時間）。

---

## 尚待釐清、之後再討論的技術細節
- v2 的「低頻決策」（升級選卡）要怎麼跟「高頻決策」（每幀移動/切招式）共用同一個
  PPO policy，是否要拆成兩個獨立的 policy head，或乾脆用 hierarchical RL。
- 若 v3 要開放連線合作，是否要换成 multi-agent 框架（例如 PettingZoo）而不是繼續用
  單一 Gymnasium `Env`。
- 是否需要在 v2/v3 導入像素觀察值作為輔助訊號（例如偵測畫面特效但數值沒即時反映的
  情況），目前判斷不需要，除非結構化觀察值被證實漏掉關鍵資訊。
